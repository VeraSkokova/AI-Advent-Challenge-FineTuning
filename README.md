# День 9: Декомпозиция инференса (Multi-stage vs Monolithic)

Этот проект демонстрирует практическое применение декомпозиции инференса на задаче анализа и маршрутизации обращений в техническую поддержку.

Код написан на Kotlin (без Spring Boot) с использованием `langchain4j-ollama`. В качестве основной модели использовалась локальная `llama3.1:8b`.

## 📌 Цель эксперимента
Сравнить два подхода к извлечению структурированных данных (JSON) из неструктурированного текста:
*   **Вариант A (Монолит):** Один большой промпт, требующий от LLM одновременно прочитать длинное письмо, составить саммари, определить тип проблемы (Enum: Incident, Request, Problem), извлечь теги и написать черновик ответа.
*   **Вариант B (Multi-stage):** Задача разбита на 3 коротких дешевых запроса:
    1.  Извлечение фактов (сухая выжимка).
    2.  Классификация (генерация строгого JSON на основе фактов).
    3.  Формирование ответа (генерация текста на языке оригинала).

## 📊 Результаты выполнения (Логи)

Эксперимент был проведен на 10 реальных тикетах из датасета `train_tickets.jsonl`. Обе архитектуры успешно (100%) справились с возвратом валидного JSON (ошибок парсинга не зафиксировано).

**Сводка по производительности:**
| Метрика | Вариант А (Монолит) | Вариант B (Multi-stage) |
| :--- | :--- | :--- |
| Успех (без ошибок парсинга) | 100% | 100% |
| Средний Latency (на тикет) | ~7 247 мс | ~11 209 мс |

Несмотря на увеличение задержки (~4 секунды на тикет из-за трех последовательных вызовов), **качество данных в Варианте B оказалось кардинально выше.**

## 🔍 Анализ качества: расфокусировка модели

Когда `llama3.1:8b` получает слишком много разноплановых инструкций в одном промпте (Вариант А), она страдает от "расфокусировки" (потери контекста внимания).

### 1. Потеря полей (Галлюцинации умолчания)
Монолитный подход (А) полностью провалил задачу по извлечению массива тегов. В 10 из 10 случаев поле `tags` либо отсутствовало, либо оставалось пустым.

Многоэтапный подход (B), благодаря тому, что на этапе №2 от модели требовалась *только* классификация, успешно генерировал теги для каждого тикета.

**Пример (Ticket 2):**
```text
// Вариант А
[A] Type: Incident
[A] Tags: (отсутствуют)

// Вариант B (Этап 2)
[B] Type: Problem
[B] Tags: [connectivity, saas]
```

### 2. Ошибки классификации из-за эмоционального шума
В сырых обращениях пользователи часто пишут эмоционально и многословно. В Варианте А модель отвлекалась на этот шум и ошибалась в классификации (Enum).

Например, обращение о проблемах с медицинскими данными (Ticket 5) и обращение о комплаенсе/безопасности (Ticket 7) монолит определил как обычные просьбы (`Request`).
Вариант B на первом этапе отфильтровал эмоции в сухие факты: `Core Issue: Data protection... Sentiment: Negative`. На основе этих фактов второй этап безошибочно определил обе проблемы как критические (`Problem`).

**Пример (Ticket 7):**
```text
// Вариант А
[A] Type: Request

// Вариант B
[B] Type: Problem
[B] Tags: [Security, DataProtection, Compliance]
```

## 💡 Выводы
1.  **Качество важнее скорости:** Для задач извлечения данных (Extraction) и сложной классификации декомпозиция инференса является обязательной. Она решает проблему расфокусировки внимания LLM.
2.  **Строгий формат:** Использование `responseFormat("json")` в Ollama/Langchain4j работает отлично, но только если модель не перегружена лишней когнитивной работой (как в Этапе 2 Варианта B).
3.  **Сбор датасетов:** Логи, собранные с помощью Варианта B, идеально подходят для формирования чистого (без "garbage in") датасета для последующего QLoRA-дообучения (fine-tuning) более мелких моделей (например, `qwen2:1.5b`).
