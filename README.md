# 🔥 День 7. Оценка уверенности и контроль качества инференса

**Статус:** Выполнено ✅  
**Стек:** Kotlin, kotlinx.coroutines, kotlinx.serialization, aallam/openai-kotlin  
**Модель:** `llama3.1:8b` (Local via Ollama)

## 📌 Описание задачи
Цель седьмого дня челленджа — реализовать механизм оценки уверенности результата языковой модели **без использования fine-tuning** для задачи, где ошибка недопустима.

Выбранная предметная область: **Извлечение структурированных данных (Data Extraction)** из пользовательских отзывов/обращений в службу поддержки. Модель должна классифицировать обращение (выбрать из закрытого списка Enum), извлечь номер тикета и написать краткое саммари.

## 🛠 Реализованные подходы

Для минимизации ошибок и галлюцинаций были применены два архитектурных паттерна:

### 1. Constraint-based (Строгие ограничения формата)
Обеспечивает гарантию того, что на выходе будет получена только ожидаемая структура данных. Реализовано в 3 слоя защиты:
- **Prompt-уровень:** Системный промпт жестко задает формат ответа и ограничивает выбор категории `enum` значениями (`REFUND`, `TECHNICAL_ISSUE`, `COMPLIMENT`, `UNKNOWN`).
- **API-уровень:** Использование `ChatResponseFormat.JsonObject` заставляет модель работать в JSON mode, отсекая текстовый "мусор" (например, приветствия или markdown-разметку).
- **Уровень десериализации:** Парсинг через `kotlinx.serialization` выступает финальным фильтром. Если модель галлюцинирует несуществующие поля или подменяет типы, парсер выбрасывает `SerializationException`, и результат превращается в контролируемый `null` (FAIL).

### 2. Redundancy (Избыточность и мажоритарное голосование)
Позволяет оценить реальную уверенность модели в ответе при работе со сложными данными:
- Каждый отзыв прогоняется через модель **3 раза параллельно** (с использованием Kotlin Coroutines `async` для минимизации Latency).
- **Мажоритарное голосование:** Система принимает ответ только в том случае, если минимум 2 из 3 сгенерированных JSON-объектов полностью совпадают по ключевым полям (категория и ID тикета).
- Если консенсус не достигнут (например, модель каждый раз выдает разные категории из-за двусмысленности текста), запрос помечается как `REJECTED`.

## 📊 Тестирование и Бенчмаркинг

Для проверки системы был собран `.jsonl` датасет из 30 примеров на основе реальных тикетов. Примеры разделены на 3 уровня сложности:
1. **Clean (10 шт.):** Понятные и четкие запросы.
2. **Edge Cases (10 шт.):** Противоречивые отзывы (жалоба на баг + просьба о возврате + перепутанные номера заказов).
3. **Noisy (10 шт.):** Имитация спама и случайного набора символов.

### 📈 Результаты инференса (Summary)

- **Total Processed:** 30 тикетов (по 3 параллельных запроса на каждый = 90 LLM-вызовов).
- **Total Rejected:** 16
  - *Система успешно отфильтровала 100% Noisy-трафика (10/10 получили статус UNKNOWN).*
  - *Система отклонила самые спорные Edge Cases благодаря несовпадению при мажоритарном голосовании, предотвратив ложные срабатывания.*
- **Total Tokens:** ~21 208 токенов.
- **Avg Latency:** ~5.5 секунд на 1 тикет.

*Примечание по Latency:* Благодаря корутинам Kotlin, выполнение трех запросов происходило практически за то же время, что и выполнение одного, эффективно утилизируя ресурсы локальной LLM.

## 🏁 Вывод
Комбинация строгого парсинга структур и мажоритарного голосования позволяет использовать базовые LLM в production-задачах с высокими требованиями к точности данных, эффективно отсекая неуверенные ответы и спам без необходимости обучать собственную модель.
