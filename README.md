# LLM Routing: Решение задания (День 8)

В этом репозитории представлено консольное приложение на чистом Kotlin, реализующее механизм интеллектуальной маршрутизации (routing) между локальными LLM с использованием **LangChain4j** и **Ollama**.

## 🎯 Архитектура

Система использует паттерн **Hybrid LLM-as-a-Judge Router**. Вместо того чтобы полагаться на самооценку маленькой модели (которая часто страдает от эффекта Даннинга-Крюгера, выдавая высокую уверенность за сгаллюцинированные ответы), мы просим быструю модель оценить *объективную сложность входящего запроса*.

- **Быстрая / Дешёвая модель:** `qwen2:1.5b` (выступает в роли первичного ответчика и классификатора сложности).
- **Сильная / Fallback модель:** `llama3.1:8b` (подключается для сложных задач и перехвата ошибок).

## 🧠 Стратегия маршрутизации и эвристики

Все запросы изначально направляются в быструю модель (`qwen2:1.5b`). С помощью **Few-Shot системного промпта** модель вынуждена возвращать структурированный JSON, содержащий сам ответ (`answer`) и оценку сложности (`complexityScore` от 0.0 до 1.0).

Роутер эскалирует запрос в сильную модель (`llama3.1:8b`), если срабатывает **ЛЮБОЕ** из следующих условий:

1. **Порог сложности (Condition A):**
   Если `complexityScore >= 0.8`. Малая модель успешно распознала сложную техническую задачу (например, написание кода, сложная математика или объяснение архитектурных различий).
2. **Защита от «ленивых» ответов (Condition B):**
   Если запрос достаточно длинный (`length > 40`), НО ответ быстрой модели подозрительно короткий (`length < 250`). Это служит страховкой на случай, если малая модель недооценила сложность и выдала поверхностный (или сгаллюцинированный) ответ.
3. **Ошибка парсинга (Condition C):**
   Если быстрая модель не смогла сгенерировать валидный JSON (частая проблема для моделей класса 1.5B при попытке вывести большие блоки кода, такие как Kubernetes YAML).

## 🚀 Главные выводы и инсайты

- **Малые модели плохо оценивают себя:** Первоначальные попытки заставить `qwen2:1.5b` оценить свою *уверенность* провалились. Модель часто генерировала неверный код или математику и уверенно ставила себе `0.9`.
- **Классификация промпта работает лучше:** Перенос фокуса с «Насколько хорош мой ответ?» на «Насколько сложен этот вопрос?» дал значительно лучшие результаты для модели на 1.5B параметров.
- **Few-Shot Prompting обязателен:** При zero-shot подходе модель оценивала простые вопросы (например, «Столица Франции») неоправданно высоко (`0.8`). Добавление конкретных примеров (Few-Shot) в System Prompt мгновенно решило проблему калибровки.
- **Гибридные эвристики:** Полагаться исключительно на оценку от самой модели рискованно. Комбинирование предсказанной сложности с детерминированными проверками (длина ответа, валидация JSON) создает максимально надежный шлюз (gateway).

## 📊 Результаты

Решение было протестировано на наборе из 10 разнообразных промптов: от базовой арифметики («2+2») до сложных инженерных задач (Kubernetes YAML, Kotlin Generics, Mamba vs Transformer).

Роутер успешно обработал простые фактические запросы на быстрой модели, корректно перенаправив все технические и сложные задачи на сильную модель. Подробные логи выполнения доступны в файле `routing_results.md`.
